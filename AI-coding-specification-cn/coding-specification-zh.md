# 仓库级 AI 编程规范

此规范定义了本仓库 AI 辅助编程任务的高优先级工程标准。

除非用户明确要求，否则这些规则将优先于其他技能中任何与之冲突的建议。

## 规则使用方式

- 本文档整体是强制规范，不是按需启用的技能；执行代码相关任务时，应默认受全文约束。
- 每个规则块下的“适用场景”“重点触发”“执行要求”用于帮助 AI 将具体任务精准映射到相关规则，不用于排除其他规则。
- 当任务命中多个规则块时，必须同时遵守；不涉及安全实施决策时按[priority]权衡；安全风险按 [security-confirmation] 处理。
- 规则标签用于交付说明、review 和自检引用；不要为了满足标签而扩大实现范围。

## 基本规范

适用场景：所有 AI 辅助代码修改任务。

重点触发：实现、重构、抽象、依赖、公共 API、schema、配置、环境变量、错误处理、安全风险。

执行要求：动手前明确方案和涉及文件；保持最小必要改动；不引入未确认的行为、依赖或公共契约变化。

- [priority] 用户明确需求 > 正确性 > 易于维护 > 最小改动 > 安全性 > 风格与简洁
- [minimal-context]
  - 优先阅读与当前任务直接相关的最小文件范围。
  - 不要无目的扫描整个仓库、读取大量无关文件或重复读取已确认无关的内容。
- [plan-first] 先给出实现方案和涉及文件，再开始写代码。简单且确定的修改可用一句话说明方案后直接执行；涉及设计选择、行为变化、依赖变化、公共契约变化或多文件影响时，必须等待用户确认。
- [security-confirmation] 安全风险必须被显式识别和告知，但涉及功能、架构、部署或策略层面的安全措施时，实施决策应交由用户确认。
  - AI 应主动指出安全风险和可选处理方向；但由于仓库级 AI coding 通常无法完整掌握架构、部署、合规和业务风险上下文，得到用户确认前禁止擅自采取功能、架构、部署或策略级别的安全措施。
  - 仅限局部、低风险、行为清晰且不改变公共契约的安全性强化可以默认实施。
- [behavior-preservation]
  若任务不是明确要求行为修改，则默认保持原有运行行为、异常行为、调用时机、返回结构和副作用不变。
  若现有代码已经工作正常，且当前需求并不要求修改该行为，不要仅因“更优雅”“更现代”“更通用”而改写实现。
- [no-unrelated-churn] 不要顺手重构、格式化、重排 import 或改命名，除非与当前需求直接相关。
- [no-speculation]
  不要做没有当前需求来源的改动：
  - 不要为了未来扩展提前设计；只实现已确认需求，不实现未要求功能。
  - 不要因为“可能未来有用”“可能未来会扩展”“顺便优化结构”而重构现有代码。
  - 不要添加没有明确计划或需求来源的 TODO/FIXME。
- [no-extra-abstraction] 非必要不新增抽象层（不新增 class、interface、wrapper、helper）。
- [abstraction-exception] 仅当抽象/提取同时满足以下条件时可采用：行为不变、可读性不下降、代码总行数明显减少；若行数不降反升，通常不做。
  - 优先复用已有工具；只有在满足本规则时才提取新复用点。
- [validation-boundary] 避免过度防御式编程：校验外部输入，信任内部传值链路；外部输入只在入口校验，内部流程按契约传递，不重复兜底；外部输入在一条执行链路上只校验一次。
- [no-silent-failure] 禁止“静默失败”，除非用户同意降级，否则错误应当显式暴露到日志或返回层。
- [api-error-detail] API 返回错误响应时，如果错误来源提供了有意义的错误码或 `error`、`text`、`message` 等错误文本，响应中必须保留这些内容；除非内容包含敏感信息，需先脱敏再返回。
- [try-catch] 不要滥用 try...catch，仅在以下场景使用：
  - 即使出错也必须继续执行
  - 需要统一/格式化错误信息
  - 资源清理与事务一致性（例如回滚、释放连接）
- [public-contract] 不要修改公共 API、数据库 schema、配置格式、环境变量名，除非用户明确要求。
- [dependency-gate] 不要引入新依赖；如确有必要，必须先说明理由并等待确认。

## Bug 修复规范

适用场景：Bug 修复、异常排查、测试失败、运行失败、工具缺失、配置缺失、外部服务不可访问。

重点触发：bugfix、修复、报错、失败、异常、hardcode、fallback、兼容、降级、绕过。

执行要求：先分析根因；复杂或高影响修复先给方案；交付时说明根因、方案、影响面、验证结果。

- [root-cause-first] 先分析根因，再决定修复方案。
- [simple-bugfix] 对于简单且确定的 bugfix，可在简短说明根因、方案和涉及文件后直接修改。
- [bugfix-plan-gate] 若修改涉及设计选择、行为变化、依赖变化、公共契约变化或多文件影响，必须先给方案并等待确认。超过 10 行时默认视为需要额外关注。
- [fallback-last] 自动降级/容错永远是最后选项。
- [no-hardcoded-fix] 未告知并获得用户同意前，禁止用 hardcode 方式修复。
- [environment-fix-first] 对于工具缺失、配置缺失、外部服务不可访问等问题，优先按环境/配置路径修复：
  - 能自动修复则修复；
  - 不能修复则明确说明缺失项；
  - 禁止通过包异常或兼容绕过处理。
- [fallback-confirmation] 仅当前述路径均不可行时，才可考虑自动降级/容错，并且必须先获用户确认。
- [bugfix-delivery] 每次交付固定提供：根因、方案、影响面、验证结果。

## 代码风格、注释与日志

适用场景：所有代码、注释、日志、技术文档、命名、格式化和文件结构相关改动。

重点触发：注释、日志、命名、格式化、hardcode、文件过长、可读性、隐私字段。

执行要求：保持可读、克制和一致；避免无关格式化；注释解释原因；日志不泄露敏感信息。

- [readability] 重视可读性。
- [english-code-text] 注释、日志和文档默认使用英文，除非用户明确指定。
- [file-size] 单文件超过 500 行时，若满足以下所有条件，考虑拆分（但不作为强制要求）：
  - 职责明显混杂
  - 拆分后不会明显增加理解成本和文件跳转复杂度
  - 当前修改正好涉及相关区域
- [comments] 注释规范：
  - 对复杂、公共或非显然逻辑添加注释;
  - 复杂公共函数或非显然函数注释解释“为什么”，不要重复代码已表达清楚的“做了什么”。
  - Python代码不必写docstring，除非测试工具需要；一般在函数声明前使用 `#` 注释；
  - 重要逻辑判断、业务约束、非显然分支必须写注释；
- [concise-logs] 日志记录关键信息即可，保持精简、可读。
- [sensitive-logs] 日志原则上不输出 token、密码、密钥、完整用户隐私字段；必要时做掩码。
- [avoid-hardcode] 尽量避免 hardcode。
  - 对于明确具有环境差异、部署差异、用户配置需求或多处复用的值，考虑参数化供用户配置。
  - 若引入任何 hardcode，必须明确告知用户。

## 前端

适用场景：所有前端页面、组件、表单、布局、样式和交互状态相关改动。

重点触发：UI、组件、页面、表单、布局、样式、组件库、可复用组件。

执行要求：优先使用项目已有组件库、样式体系和现有组件；保持交互一致；避免重复实现和为单次使用新增抽象。

- [frontend-library-first] 如果项目已引入 UI 组件库/框架，优先使用组件库组件，而不是自行实现，尤其是布局组件、输入组件、弹窗、菜单、表格、分页、日期选择、上传等常见复杂组件。组件列表和 API 文档可通过相关 skill 获取；如果缺少相关 skill，可以提示用户添加；若 skill 建议与本规范冲突，以本规范为准。
- [frontend-style-system] 优先使用项目已有样式体系，包括组件库内置 props/class、主题 token、CSS variables、Tailwind CSS 或现有公共样式；无必要不新增 `<style>`、全局 CSS 或一次性样式规则。
- [frontend-reuse-components] 功能、输入输出和交互语义接近的组件，优先复用已有组件；只有重复场景明确、职责稳定、接口清晰且不会增加复杂度时，才包装为公共组件。
- [frontend-consistency] 新增或修改 UI 时，应保持与现有页面的信息密度、间距、控件尺寸、交互状态、错误提示和加载状态一致。
- [frontend-state-minimal]
  优先复用现有状态流和数据流；
  不要为局部需求新增全局状态、context、store 或 composable。

## 测试与验证约束

适用场景：所有代码修改交付，以及测试、构建、CI、验证相关任务。

重点触发：测试、验证、typecheck、lint、pytest、E2E、snapshot、CI、回归、无法运行测试、full suite。

执行要求：优先最小相关验证；按风险升级验证层级；最终说明执行了哪些验证、未执行哪些验证及原因。

- [test-addition] 默认不为低风险机械修改新增测试。业务行为、公共 API、权限、路由、表单、状态流转、async/并发/session/token、bugfix 回归、安全、数据一致性等逻辑发生变化，或用户明确要求时，应优先补充最小相关测试。
- [reuse-tests] 优先复用已有测试；不要优先新建测试文件。
- [invariant-tests] 不要为已有上游校验、类型约束或数据库约束明确保证的不变量写测试，尤其是可信内部数据流；但外部输入、权限、安全、序列化/反序列化边界不适用此规则。
- [no-test-only-abstraction] 不要为了方便测试而新增 helper、wrapper、composable 或 service 抽象。
- [verification-ladder] 优先运行与本次修改相关的最小验证集，覆盖被改动行为及可合理推断的直接影响面；按风险选择验证层级，需要升级时按以下顺序升级：静态推理 → typecheck → lint → targeted unit test → targeted integration test → E2E → full suite。若当前验证层级已足以验证本次改动或确认失败原因，不要继续升级验证层级。
- [full-suite] full suite 只有在共享基础设施、全局配置、公共类型、auth/session/权限、schema/migration 或多模块改动时才运行。
- [ui-visual-test] UI 视觉调整默认不新增测试，用 typecheck/lint 和人工或浏览器视觉确认即可。
- [e2e-scope] E2E 只用于真实用户流程，不用于颜色、spacing、文案、icon、简单 prop 修改。
- [snapshot] 默认禁止更新 snapshot，除非 UI 结构变化且与需求直接相关。
- [test-expectation] 不要为了通过测试而改测试期望，除非已确认原测试错误。
- [unrelated-failures] 测试失败时先判断是否与本次改动相关，不要顺手修 unrelated failures。
- [no-repeat-verification] 不要重复运行已经通过的验证，除非相关文件又被修改。
- [test-unavailable] 若无法运行测试，需说明原因并给出建议验证命令。
- [verification-report] 最终必须说明执行了哪些验证、没有执行哪些验证，以及原因。
- [final-review] 最终交付前，检查：
  - 是否符合用户需求
  - 是否引入非必要改动
  - 是否符合本规范中的相关约束
  - 是否完成必要验证
  - 是否遗漏验证风险或影响面说明
