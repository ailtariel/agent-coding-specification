# Web 前端编码规范

本规范定义目标工作区或受影响仓库内 Web 前端工作的强制性、框架中立工程规则，适用于页面、布局、组件、样式、状态、数据同步、交互、可访问性和前端开发工具。

本规范扩展 [`coding-specification.md`](coding-specification.md)。项目设计文档定义产品特定行为，框架和 UI 库 skill 提供实施细节；两者都不能削弱本规范。

## 规则使用方式

- 无论使用何种框架、渲染模式、组件库或状态管理库，所有 Web 前端任务都必须遵守本文档。
- 同时应用所有相关规则块。本文档与用户已确认的项目设计决策冲突时，实施前停止并确认预期例外。
- 规则标签用于计划、审查、交付说明和自检。不得仅为满足某个标签而扩大实施范围。
- 框架特定的 API、文件类型、宏、hook、composable、组件和格式例外应放入对应框架或 UI 库 skill，不得写入本文档。

## 通用规则

- [ui-documentation-exemption] 除非用户明确要求，UI 布局、样式和界面交互的设计、实现与调整，不得为此创建或更新设计文档、实施计划、变更记录、验证报告等文档文件，也不得以完成文档或文档确认为实施前提。本豁免优先于通用的文档创建、更新和实施阶段记录要求。
  - 界面交互包括展开与收起、弹窗开关、悬停反馈、焦点移动、滚动和展示切换等不改变业务语义的行为。局部 UI 状态变化、展示已有数据或调用既有功能，本身不构成数据处理或业务功能变更。
  - 只有新增或改变数据获取、计算、转换、持久化、接口契约、业务规则或业务流程的部分，才进入文档需求判断；涉及这些内容也不意味着必须新增文档，应根据需要说明和保留的设计决策确定，优先更新已有相关文档。
  - 同一任务同时涉及 UI 和功能变化时，文档仅记录需要说明的功能与数据处理变化，不扩展记录布局、样式或纯界面交互细节。页面数量、修改文件数量、视觉复杂度或分阶段实施，不得单独触发 UI 文档要求。
  - 修改说明和验证结果直接在对话中交付，不另行生成文档文件。
- [web-existing-stack] 保持项目既有的前端框架、组件库、状态流、路由模型、样式系统、formatter 和构建工具，除非用户明确批准变更。
- [web-version-boundary] 应用特定版本的 API、migration 或 breaking-change 指导前，先确认已安装的依赖版本。
- [web-no-parallel-system] 不得为局部需求引入平行的组件库、状态管理系统、utility CSS 框架、样式系统、路由系统或数据获取层。
- [web-existing-patterns] 引入新模式前，先检查现有的同类 page、layout、component、状态流和样式模式。
- [web-single-owner] 每个 application shell、layout region、page region、主滚动容器、overlay、状态来源和反馈渠道必须有一个明确所有者。
- [web-locality] 页面特定的行为、状态、样式和组件应留在最近的 feature 或 page 边界内。只有形成真实的跨页面职责后，才提升其层级。

## 文件组织与职责边界

以下示例展示文件归属，`*` 表示由技术栈决定的文件扩展名。目录和文件按需创建，已有等价结构或框架约定时沿用原结构。

```text
src/
├── layouts/
│   └── {layout}/
├── pages/
│   └── {page-or-page-group}/
│       ├── components/
│       │   └── {component}/
│       ├── modules/
│       │   └── {module}/
│       ├── Page.*
│       ├── types.*
│       ├── store.*
│       ├── service.*
│       └── useXxx.*
├── shared/
│   ├── components/
│   │   └── {component}/
│   ├── modules/
│   │   └── {module}/
│   └── libs/
├── routes/
└── stores/
```

页面和模块自己的状态、类型及数据访问文件跟随其所有者；顶层 `stores/` 只放应用级状态。组件的实现和私有样式放在对应 `{component}/` 内，简单组件也可直接平铺。

- [web-project-structure] 新增或调整文件时，沿用项目及框架既定的目录约定，按实际职责聚合相关文件，不按大小或名称归类；只创建当前需要的目录和层次，不为套用模板重排项目或拆出仅作透传的文件。文件归属和依赖应遵循以下职责边界：
  - Application 负责应用启动、全局配置和跨页面能力，不承载具体页面的内容与业务操作。
  - Layout 负责共享导航、页头等应用外壳及页面出口，不承载页面业务；页面不得重复实现所属 layout 已提供的外壳。
  - Page 或相关页面组负责自身的内容组合、业务操作和局部状态；私有组件、类型、数据访问与样式就近组织，不分散到全局目录。
  - Component 负责展示与交互，可以拥有局部交互状态；module 拥有业务规则、数据和流程，可以包含组件；lib 提供与具体业务无关的技术能力。
  - 仅在出现真实的跨功能复用时，将相应组件或模块及其私有依赖移入共享范围；共享代码通过公开接口供使用方调用，不反向依赖具体页面的私有实现。

## 组件抽取

- [web-component-extraction] 抽取组件或模块应有独立职责、真实复用、复杂逻辑隔离或独立编排的需要，不得仅为减少行数、移动模板代码或增加包装层而拆分。
  - 无复用需求且内容简单，或与父级高度耦合、拆分需大量传递依赖时，优先保留原结构。
  - 抽取时迁移完整职责及私有依赖，通过输入、输出和扩展点适配使用方；不得只共享外观而复制业务逻辑，也不得按页面名称或路由分支适配。单一使用方的组件保留在所属功能内。

## API 访问

- [web-api-layer] 页面和 UI 组件通过所属功能的数据访问层调用 API，不直接发起请求。数据访问层复用项目既有客户端处理认证、基础地址、通用请求头和错误转换；业务代码只使用相对路径，不硬编码服务地址或代理目标。确需绝对地址、独立客户端或其他传输方式时，实施前说明原因、归属和影响。

## 组件复用与 UI 库

- [web-reuse-order] 实现所需组件或业务能力前，按以下顺序查找并选择：项目内可直接复用的组件/模块 → 将项目内职责相同的已有实现抽取为可复用组件/模块 → 查询项目 UI 库中的可用组件 → 自定义实现。只有前一层没有职责匹配且适合复用的方案时，才进入下一层，不得跳过查找而直接手写。
  - 使用库组件时，先使用公开 API 和扩展接口；能力不足时才补充样式或行为，不另写 DOM 或事件机制替代组件已有的交互与可访问性能力。
  - 无论复用还是自定义，均须遵循项目既有的信息密度、间距、控件尺寸、交互反馈和响应式模式。

## 数据来源、数据流与反馈

- [web-state-source] 同一份业务数据由满足使用范围的最近所有者管理，共享消费者读取同一权威来源；不得把复用逻辑误当成共享状态，或为复用代码默认引入全局状态。
  - 展示值和派生值从源数据计算并自动更新，不另建需人工同步的可写副本。独立编辑、取消或延迟提交可使用编辑副本，但须明确初始化、提交和丢弃方式，不直接修改共享的已保存数据。
  - 修改通过所有者提供的操作更新或失效相关来源，使消费者通过既有响应式机制获得结果；不得用直接修改 DOM、重复维护副本或强制刷新页面掩盖数据流断开。
- [web-feedback-owner] 字段和页面反馈由对应表单或页面负责；系统级反馈、全局错误及跨页面提示使用应用级机制，不各自重复实现。明确处理加载、空结果、失败、禁用、选中、成功和数据过期状态，不依赖偶然的渲染分支。

## 弹窗操作顺序

- [web-dialog-action-order] 弹窗同时包含应用结果与放弃结果的操作时，在LTR下，应用操作（如保存、删除、应用筛选）放左侧，放弃操作（如取消、关闭）放右侧。没有放弃操作的交互不必人为添加取消按钮；用户已确认不同产品约定时，遵循该约定。

## CSS 与样式归属

- [web-style-colocation] DOM 与私有样式由同一组件负责，样式按框架约定随组件组织、移动并限制作用域，不为缩短文件拆入无关文件，也不为局部需求提升到全局。公共样式只承载应用基础样式和稳定的共享视觉规则，优先复用既有主题、token、组件默认值或共享组件，不为单页例外新增公共配置。
- [web-style-replacement] 调整样式时，修改原有声明并清理被替代的规则，不靠追加重复声明、提高优先级或强制覆盖抵消旧实现；主题、断点和交互状态所需的明确变体可以保留。间距和尺寸设置在实际负责布局的元素上，不为单个样式属性增加包装层；优先使用既有语义配置和响应式能力，产品或平台确有约束时可使用固定值。

## 移除废弃实现

- [web-remove-obsolete] 功能或视觉结构被移除、替换时，同步清理本次变更涉及且不再使用的 DOM、样式、状态、逻辑和引用，不得以永久隐藏旧节点代替移除；仍有明确交互用途的临时隐藏不属于废弃实现。

## 交互、表单与可访问性

- [web-accessibility] 新增或调整交互时，使用语义元素和既有 UI 库组件，不以普通容器的点击事件替代控件能力，也不为视觉效果移除交互反馈。
  - 每个表单控件和仅图标控件须有可访问名称；表单控件保留校验、禁用、提交状态及错误反馈。
  - 保留键盘导航、输入法组合输入，以及弹层的触发语义、焦点恢复和 Escape 行为；焦点、悬停、激活、选中、加载和禁用状态须有可见反馈。

## 双向与 RTL 布局

- [web-logical-direction] 布局须支持双向界面；方向及方向性间距、对齐使用统一配置或 token 来源，不在页面和组件中重复判断 RTL。优先使用 inline/block/start/end 等逻辑方向属性；只有明确依赖物理方向的视觉需求才使用 left/right 等物理方向属性。

## 国际化与用户可见内容

- [web-i18n] 应用界面文本，包括标题、导航、控件文案、占位符、状态提示、校验消息和错误兜底文本，统一使用项目既有国际化机制；外部或用户提供的业务内容及运行日志不适用，后端已本地化的业务数据不能替代界面文本的国际化。
  - 消息须通过项目配置的语法编译；只有语义和插值契约一致时才复用消息键，不因文本相同就合并。
  - 错误提示保留有用的来源详情，并对敏感信息脱敏；不得用通用翻译文案覆盖具体错误。

## 格式化与修改范围

- [web-formatting] 前端源码和配置文件以项目 formatter 为唯一格式化依据，不手工对齐或为个人偏好修改配置；格式化限于任务涉及的文件，已有格式检查须在交付前运行。

## 测试用例设计与使用

- [web-persistent-test-scope] 长期用例只验证数据流和稳定业务行为，不固化 DOM、样式、展示文案、截图及 UI/UE 交互呈现。按断言内容判断，使用浏览器或挂载组件不影响分类；按改动风险覆盖相关正常、异常和边界行为，优先复用已有用例，不以数量或覆盖率代替价值，也不为测试方便新增生产抽象。
- [web-data-flow-tests] 数据流测试须执行真实被测逻辑，验证本次改动涉及的输入、处理、状态变化及消费者结果；风险跨越多个环节时覆盖必要协作，不能以单个函数正确或调用发生代替整条数据流正确。
  - 可替换测试范围外的依赖，不得 mock 掉被测过程或在测试中重写实现。
  - 期望来自需求和业务契约，须能区分正确与错误行为；不照抄实现、不用被测代码生成期望，也不锁定源码写法、变量名、内部步骤或组件组织。业务契约未变时，不因重构或测试失败而迎合当前实现修改期望。
- [web-temporary-ui-tests] UI/UE 在本次开发中通过手工、浏览器或临时自动化验证；临时用例及辅助资产放在正式测试目录之外，不进入功能提交，并在验证完成后清理。UI/UE 不固化不代表可以省略验收。
- [web-verification] 选择足以验证本次改动的最小检查组合，分别说明静态检查、业务测试和 UI/UE 验收实际覆盖及未验证的范围，不以其中一类通过代替其他类别的验证结论。

## 最终审查

交付前按本次修改适用的规则检查职责边界、行为和验证结果，修正偏差；不因自检扩大修改范围。
