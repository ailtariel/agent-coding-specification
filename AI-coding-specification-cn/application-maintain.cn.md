# 应用维护

本文档中的所有相对文件和目录位置，包括 `README.md`、`.env*`、`backend/` 和 `web/`，均从拥有该应用产物的目标工作区或受影响仓库的根目录解析。除非存储本权威规范的仓库本身就是任务目标，否则这些位置绝不指向该规范仓库。

## 变量管理

新增、读取、移动或移除任何配置值之前，必须先将其分类为引导环境变量或受管运行时设置。

分类决策必须先于文件、API、迁移或 UI 变更的选择。不要从“它应该放在哪个 `.env` 文件中？”或“它应该放在哪个 Settings 标签页中？”开始，而应从该值的用途和必须可用的时间开始判断。

使用以下决策规则：

1. 如果该值在后端连接数据库或读取 `system_settings` 之前就是必需的，则将其保留为引导环境变量。
2. 如果该值用于标识部署或进程、控制本地开发工具，或者必须由运行平台在应用启动前注入，则将其保留为引导环境变量。
3. 如果该值控制应用启动后的功能行为、可以在 Admin Settings 中显示或编辑，或者应由 `/config/web` 返回给浏览器，则将其设为受管运行时设置。
4. 如果该值敏感，仍应先根据生命周期进行分类。受管的敏感运行时值应放入设置注册表并由后端掩码处理，不得放入前端环境文件或目录元数据。
5. 如果无法确定，除非该值必须在数据库可访问之前使用，否则默认将其设为受管运行时设置。

### 引导环境变量

环境变量仅用于必须在读取数据库和 `system_settings` 之前可用的值，或者用于部署或进程标识。有效示例包括：

- `ENV` 选择、dotenv 加载、服务器进程设置和本地开发服务器连接配置。
- 数据库连接和 schema 设置。
- 启动期间所需、由部署注入的标识或进程级值。
- 有意传递给子进程环境的值。

运行时功能模块不得为实现功能行为而直接调用 `os.getenv`、`os.environ.get`、`process.env` 或 `import.meta.env`。如果一个值可以合理地在 Admin Settings 中编辑，或者应该在 Settings 页面中可见，则必须将其表示为受管运行时设置。

引导环境变量必须记录在实际提供它们的部署模板或本地开发模板中。不得仅为了让受管运行时设置可配置，就将其添加到 `.env`、Helm values、Docker compose 或生成的前端环境配置中；应将其放入设置注册表。

常见的引导配置位置包括：

- 如果存在本地开发示例，则位于 `README.md` 或提交到仓库的 `.env*` 模板中。
- 前端构建或开发引导文件仅用于构建时或开发服务器相关事项。
- 后端引导设置位于 `backend/src/shared/settings.py`。
- 当相应部署路径需要该变量时，位于 Helm values 和 Docker compose 文件等部署模板中。

引导配置同步规则：

1. 可选变量：
   - 值可以为空。
   - 键必须存在。
2. 必需变量：
   - 必须添加到受影响运行路径所适用且已提交到仓库的每个本地或部署模板中。
   - 在对应文件或文档中添加注释。

值约定：

1. 生产部署模板应避免提交真实密钥值。
2. 开发模板可以包含安全的本地默认值。
3. 如果不存在安全的默认值，则将值保留为空，并记录必须提供的内容。

### 受管运行时设置

受管运行时设置是由后端设置注册表定义、以数据库为支撑，并且可以选择显示在 Admin Settings UI 中的值。`system_settings` 表只存储用户修改的覆盖值。默认值应位于代码中，不应存在于预先写入的种子行中。重置设置时，应删除数据库覆盖值并重新显示注册表默认值。

功能模块必须通过共享注册表访问器读取受管值，例如 `backend/src/module/system_setting/runtime_settings.py` 中的 `get_setting_value(...)` 或 `get_setting_values(...)`。除非正在实现注册表本身，否则不得直接读取 `system_settings` 获取功能配置。

敏感受管值必须在后端注册表中标记为敏感，并且不得通过管理响应、`/config/web`、日志、占位符或仅供前端使用的元数据暴露。

`restart_required` 是面向用户的提示，不是写入约束。只有新值在进程重启前无法生效时，才将其设置为 `true`。如果系统可以实时应用该值或对其重新初始化，则使用 `restart_required=false`，并接入适当的运行时重新初始化行为。

### 注册表和目录位置

后端权威注册表：

- 文件：`backend/src/module/system_setting/runtime_settings.py`
- 主要定义：`SettingSpec`、`_spec(...)`、`UNIFIED_SETTINGS`
- 公共读取和应用辅助方法：`get_setting_value(...)`、`get_setting_values(...)`、管理设置 payload 构建器、`/config/web` payload 构建器，以及运行时重新初始化分发。

后端注册表只负责与后端相关的事实：

- 稳定的领域键，例如 `logging.log_level`
- `system_settings` 中使用的存储分类和键
- 默认值来源，可以是常量、`Settings` 属性或 resolver
- 值类型、可编辑性、敏感性、校验规则和允许值
- 重启和运行时重新初始化行为
- 是否向管理设置公开，以及是否对客户端可见

前端 Settings 目录：

- 文件：`web/src/settings/settingsCatalog.ts`
- 用途：Settings 页面分组、标签、描述、占位符、控件和仅供前端使用的校验提示。

前端目录不是安全、校验、持久化或客户端暴露的权威来源。不得引入后端注册表中缺失的设置键。不得复制后端敏感性判定，也不得将前端目录中的后端校验副本作为唯一强制措施。

Admin Settings API：

- `GET /api/v1/admin/settings`
- `PUT /api/v1/admin/settings/{domain_key}`
- `DELETE /api/v1/admin/settings/{domain_key}`

客户端运行时配置 API：

- `GET /config/web`
- 返回的键只能来自标记为 `client=true` 的后端注册表条目。
- 客户端可见设置不得包含凭据、token、私有路径、私有连接字符串或仅供服务器使用的值。

### 新增或维护变量

对每个新增或变更的变量使用以下检查清单：

1. 使用上述决策规则对值进行分类。选择不明显时，在实施说明中记录理由。
2. 对于引导环境变量，将字段添加到 `backend/src/shared/settings.py` 或相关前端或构建引导路径，然后根据上述规则，只更新适用且已提交到仓库的本地或部署模板及文档。
3. 对于受管运行时设置，在 `backend/src/module/system_setting/runtime_settings.py` 中添加 `SettingSpec` 条目，并设置正确的领域键、存储分类和键、值类型、默认值来源、可编辑性、敏感性、重启行为、运行时重新初始化行为以及 `client` 暴露配置。
4. 当有效值受到限制时，在注册表中添加后端校验或 `allowed_values`。如果值是动态发现的，后端应公开 `allowed_values`，避免前端硬编码过时选项。
5. 更新功能代码，使其通过注册表辅助方法读取该值。移除对该值的直接环境读取和直接 `system_settings` 查询。
6. 如果设置应显示在 Admin Settings 页面中，应在后端注册表键存在后，在 `web/src/settings/settingsCatalog.ts` 中新增或更新对应条目。
7. 如果浏览器需要在运行时使用该值，将后端规范标记为 `client=true`，并验证 `/config/web` 只返回前端预期的公共键值结构。不得仅因为某个值出现在 Admin Settings 页面中，就将其暴露给浏览器。
8. 如果重命名或迁移旧数据行，在 `backend/src/shared/db/migration/` 下添加数据库迁移。迁移可以重命名或删除旧覆盖值，但不应为受管设置写入默认值数据行。
9. 当行为、API 结构、掩码、校验、运行时重新初始化、迁移行为或前端渲染发生变化时，新增或更新针对性测试。

### Settings UI 文本规则

维护 `settingsCatalog.ts` 时使用以下文案规则：

- `placeholder` 应回答“我应该在这里输入什么？”。适用时应包含预期格式和示例。
- `description` 应说明运行时效果、变更何时生效，以及任何值得注意的副作用。
- 选择控件通常不需要占位符。
- 不得在标签、描述或占位符中放入密钥、真实凭据、仅供内部使用的路径或隐藏策略详情。
- 标签应保持简洁稳定。修改标签不得改变后端键或存储键。
