# 如何编写规则和 Skill

本文约定本仓库中规则的定位与提炼方式，适用于新增、修改和审查 `AGENTS.md` 及规则文档。以下对规则的分类是本仓库的约定；官方资料作为编写指引的补充参考。

- 规则分为两类：**约束错误**与**约束实践**。
- **可复用性：**规则必须针对可重复出现的编码或工作范式，且未来很可能再次适用。一次性指令或仅针对当前任务的决策不提炼为长期规则。
- **约束错误：**当 AI 反复出现同一类错误范式时，将其提炼为简练的约束，优先指出“AI 不该怎么写”。必要时可补充“AI 该怎么写”，但不强制提供。示例：[`coding-specification.cn.md`](coding-specification.cn.md) 中的 `[no-silent-failure]`，约束静默失败。
- **约束实践：**当 AI 在同一具体场景中反复采用不一致或不佳的实施方式时，提炼规则，限定该场景下统一采用的实施方式或实践范围，并写清适用边界。用户明确选定的实践或个人偏好也可作为约束依据，不必包装成通用最佳实践。示例：[`coding-specification.cn.md`](coding-specification.cn.md) 中的 `[e2e-scope]`，限定 E2E 测试只覆盖真实用户工作流。
- **内容边界：**规则只保留针对上述问题的必要约束，不涉及通用、常规、教条式知识，不扩展为编码教程。为防止目标错误，可以规定选择依据、职责归属、必要顺序和完成条件；实现这些约束的详细操作、框架 API 用法和技术参考归入 Skill。例如，[移植规范](feature-porting.cn.md)中的 `[port-copy-then-adapt]` 规定先复制、再适配、确认行为等价后才删除，以防止移植遗漏或擅自重写。
- **简洁标题：**尽量为每条规则提炼一个能直接表达约束主题的简短标题，避免空泛或重复正文。
- **单条完整：**一条规则应独立、自洽地表达一项完整约束，包含判断和执行所必需的条件与边界，不依赖其他条款补全。同一主题的不同方面可以分别成条，但不得将一项约束的必要内容拆散到多条规则中。
- **适用范围与例外：**写清约束适用的任务、对象或环境，区分“禁止”“默认”“优先”和“仅当”；存在合理例外时明确条件，避免将局部约束泛化为全面禁止。例如，[前端规范](web-frontend.cn.md)中的 `[web-state-source]` 禁止重复维护派生状态，但允许有明确初始化、提交和丢弃方式的编辑副本。
- **约束行为而非表面写法：**从具体错误中提炼可复用的判断依据，覆盖语义相同的写法；不得让 AI 通过换语法、增加包装或转移位置规避约束。例如，`[try-catch]` 按错误处理职责划定边界，同样适用于 `Promise.catch()`，不能简化为禁止使用 `catch`。
- **分层与衔接：**共用约束保留一个权威定义，专项规则只规定特定场景的差异，通过入口按任务路由。引用用于定位相关规则，不替代当前条款的必要内容；需要引用的规则使用稳定标签。规则涉及的项目路径应明确所属目标，不能误指向存放规范的仓库。
- **规则一致性：**不同规则不得在同一适用条件下提出相互矛盾的要求。专项例外应明确适用条件及所覆盖的通用要求；新增或修改规则时，同步检查并消除受影响条款中的冲突，不将矛盾留给执行者自行解释。
- **检查约束的副作用：**检查规则能否阻止目标错误、统一目标实践，以及是否误伤正常行为。不得仅因文件数、行数或阶段数机械增加拆分、文档、测试或审批要求；需要确认的条款应区分尚未授权的决策与已授权的执行步骤，避免重复审批或提前停止。
