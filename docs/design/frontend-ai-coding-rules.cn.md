# 前端 AI 编码问题范式与分层规则设计

日期：2026-09-10。状态：规则设计稿，尚未合入生效规范或 skills。

## 目标与边界

本设计从 AI 编码的重复错误中提炼通用约束，重点提高前端数据流测试的价值，不再围绕某个项目的具体缺陷制定修复清单。

长期保留的前端测试以数据流和稳定业务行为为重点；UI/UE 的结构、样式和交互呈现验证属于当次开发验收，不固化为回归用例。规则保持现有分层：通用约束属于 agent-coding-specification，Vue/React 与 Vuetify/Ant Design 的具体落实方式属于 skill-sets。

设计不要求引入新的测试框架、状态库、请求库或组件库，不要求全项目重构，不按错误实例数量累积规则。当前任务之外的既有测试和代码也不因本设计自动获得删除或修改授权。

## 1. 规则层次与职责

| 层次 | 归属 | 应规定的内容 | 不应承担的内容 |
| --- | --- | --- | --- |
| 通用编码规则 | agent-coding-specification 的 coding-specification | 最小验证范围、业务契约优先、避免自证测试、变更和测试的真实性 | 某个前端框架的状态 API、组件库用法 |
| Web 通用规则 | agent-coding-specification 的 web-frontend | 数据所有权、异步有效性、查询一致性、复用和样式边界；永久数据测试与临时 UI/UE 验收的划分 | Hook/composable、框架文件格式、组件名称、特定测试工具 API |
| 框架规则 | skill-sets 的 Vue / React skill，以及相关状态管理、路由 skill | 将通用约束映射到响应式、状态实例、生命周期、路由复用、组件文件和实际测试运行方式 | 重新定义通用测试政策、按另一框架的限制约束当前项目 |
| 组件库规则 | skill-sets 的 Vuetify / Ant Design skill | 使用已安装版本的组件、受控数据接口、事件语义、表单状态、主题与样式扩展接口 | 用库内部状态替代业务权威状态，或另建一套通用规范 |

`web-project` 入口只识别技术栈并路由到相关 skill。规则只有一个权威定义，其他层引用并补充；不把整套通用条款复制到每个 skill。

中文草稿和生效英文规则保持语义一致。设计稿不是另一个供编码任务自动加载的规则入口。

## 2. AI 编码的问题范式

下表描述从产物中可观察的失败机制，不推断模型内部心理，也不假定每次错误都由同一个原因造成。

| 范式 | 失败机制 | 规则要约束什么 |
| --- | --- | --- |
| 只解决当前文件 | 查到一个 API 或画出一个组件就开始实现，遗漏同业务的其他消费者和既有约束 | 新增前确认已有责任所有者，复用稳定契约；修改覆盖直接消费者 |
| 复用外观，复制业务 | 表格或表单被抽取，但查询、提交、失效和错误处理在各页面重新实现 | Component 复用视图交互；Module 复用业务责任及数据流，不能只共享 DOM |
| 把代码复用当成状态共享 | 多次调用同一逻辑入口，实际创建多份可写状态；或复制输入值后不再跟随源 | 声明状态实例与生命周期；派生值保持派生关系，共享消费者订阅同一所有者 |
| 把当前值当成完整数据身份 | 忽略用户、组织、查询条件、资源或版本，使类型相同的数据被错误互换 | 明确查询身份、结果有效范围和提交权限 |
| 只验证顺序成功路径 | 默认请求按顺序完成、操作不重叠、页面不会切换、请求不会局部失败 | 对受影响的数据流验证有区分力的时序、失败和上下文边界 |
| 用兜底掩盖未知 | 将异常统一转换为空值，或由局部操作整体覆盖其他状态 | 保留失败语义，限制写入字段；编辑缓冲有独立边界 |
| 自制已有能力 | 用简单 DOM 和事件快速仿制库控件，再不断补交互与样式 | 优先项目封装及库公开契约；定制仅承担实际缺失的能力 |
| 追加补丁而不完成替换 | 修改通过更后面的 CSS、更高优先级或隐藏旧 DOM 生效，旧实现仍存活 | 修改责任源头，清理已替代节点、样式、监听与旧入口 |
| 测试复述实现 | 从刚写的代码生成源码正则、同构期望值或大量 stub，得到自证结果 | 期望来自契约；执行真实被测链；证明测试能识别对应错误 |
| 把测试数量当成质量 | 大量固化易变 UI，遗漏共享数据、异步和业务状态边界 | 以业务风险与可检测缺陷选择测试，不以数量、覆盖率或全绿代替证据 |

## 3. 前端测试政策

### 3.1 按断言责任划分，而不是按工具和文件名划分

**永久测试验证稳定的数据与业务契约；临时验证检查当前 UI/UE 的正确实现。**

| 验证对象 | 是否固化 | 边界 |
| --- | --- | --- |
| 输入到查询/提交参数的转换，筛选与分页语义 | 是，按改动风险选择 | 验证实际发送或交给边界的业务参数，不锁死事件处理函数的名字 |
| 状态派生、共享消费者同步、缓存更新与失效 | 是 | 验证真实状态来源及消费者，不只验证一个脱离接线的纯函数 |
| 请求乱序、上下文切换、取消后的回写、重叠 mutation | 是 | 验证状态与副作用仍属于正确资源和操作 |
| 编辑草稿、提交成功、失败恢复、字段级合并 | 是 | 验证业务状态和持久化行为，不固定表单排版或错误消息位置 |
| 数据错误、空结果、部分失败的分类与传播 | 是 | 验证错误事实到达消费边界；提示框形态属于临时验证 |
| 业务权限、业务状态转换和具有稳定契约的关键流程 | 是 | 前端测试不能替代后端权限验证；界面隐藏不等于授权 |
| DOM 层级、模板/JSX、CSS 类、颜色、尺寸、间距、图标、截图 | 否 | 当次视觉或浏览器验收；不保留源码快照、截图基线和选择器断言 |
| hover、焦点移动、动画、键盘导航、响应式排布、RTL 呈现 | 否 | 按受影响范围做当次 UI/UE 验收；不固化为长期交互用例 |
| 纯展示文案及翻译文本 | 否 | 若涉及稳定的业务 code、数据序列化或语言资源解析契约，则单独验证该数据契约 |
| 类型、构建、模块依赖等静态约束 | 不是 UI 回归测试 | 使用既有类型检查、构建和适合该约束的静态工具，不能替代数据流验证 |

浏览器可以只是业务测试的驱动方式。例如，提交操作后验证正确资源被更新，断言对象是业务结果，可以保留；断言该提交按钮位于某个 DOM 层级则不保留。应优先选择能够证明目标契约的最小运行边界，避免为简单业务断言绑定整页操作路径。

混合用例中的业务断言与 UI/UE 断言应分离。不能因为用例还断言了一个业务结果，就把大批 UI 快照一起固化；也不能因为用例需要挂载组件，就将真实数据流测试全部排除。

### 3.2 永久测试的重点：数据流，而非只有数据加工函数

需要验证的链路是：

```text
外部输入 / 业务操作 / 上下文变化
    → 查询或命令参数
    → 数据访问边界
    → 权威状态提交、失效或错误传播
    → 派生状态与实际消费者
```

单独测试排序、格式化等纯函数，不能证明页面绑定了正确的源。单独确认 API 被调用，也不能证明它使用正确参数、结果被正确提交、其他消费者已同步。

按实际变更选择以下不变量，不要求每次把全部组合跑一遍：

- **来源与传播**：源数据变化后，相关消费者通过真实订阅或输入绑定获得新值；不存在无意的独立可写副本。
- **查询一致性**：记录、总数和应联动的统计属于同一业务筛选范围；分页子集不能冒充完整集合。
- **身份隔离**：用户、组织、资源及其他影响结果的上下文变化后，旧范围数据不被认作新范围的有效结果。
- **时序有效性**：失效请求不能改变当前数据、错误或 loading；合法并行任务遵循各自身份和提交策略，而不是机械地全局“最后请求获胜”。
- **写入边界**：局部更新不覆盖无关字段；失败回滚不能撤销之后已成功的更新；编辑草稿与已保存值保持明确关系。
- **失败可辨**：真正空结果、尚未取得结果、失败与部分成功能够区分；失败事实不会在中间层被吞掉。
- **生命周期**：共享实例与独立实例的行为符合约定；销毁、上下文切换和重复挂载不会留下错误回写或非预期副作用。
- **请求与副作用规模**：需要去重、幂等或并发限制时验证这些契约。只有请求次数本身就是契约时才断言次数，不用脆弱调用顺序描述内部实现。

### 3.3 约束 AI 生成测试的质量

建议补充以下可直接执行的规则。

**A. 先定义业务期望，再选择验证方式。** 测试应能说明保护哪个数据契约、什么错误实现会被它识别。期望值来自需求、接口契约或独立确定的输入输出，不照抄待测算法，也不用待测函数自身生成 expected。

**B. 执行真实被测实现。** 长期测试通过实际模块入口执行真实 action、service、状态所有者和必要的消费者。禁止读取源码检查变量名、Hook 名、setter 出现次数、模板片段或 CSS 来冒充数据流测试；禁止复制业务实现到测试中。源码/AST 提取最多作为一次性诊断证据，不能代替完整模块和生命周期验证。

**C. 替换外部边界，保留目标链路。** 网络、时钟、存储等外部依赖可按需替换；不得 mock 掉测试声称覆盖的状态转换、查询适配、订阅或提交过程。不能以“被 stub 的 action 被调用”作为 action 数据行为已验证的证据。每种测试替身的保真程度应与其所证明的契约一致。

**D. 控制具有区分力的输入与时序。** 多使用能让错误实现得到不同结果的数据，避免全为空、全部同值或只有单一消费者。并发测试应能控制完成顺序，不靠固定等待和碰运气的延迟。无需枚举所有边界，只覆盖与本次变更相关的真实失败机制。

**E. 不把纯逻辑测试当成接线证明。** 当风险在状态所有者、查询参数绑定或消费者同步时，应包含最小必要的真实接线；如果只测了某个独立函数，交付中明确其覆盖边界。

**F. 证明测试有辨别力。** 新增重要回归用例应有证据表明对应错误会失败、修复后会通过。优先利用已知失败基线或能区分正确/错误实现的对照输入；必要时做一次局部临时错误注入验证。此条不要求引入 mutation-testing 平台、保留错误实现或把每个小改动都扩展成实验。

**G. 正确重构不应迫使业务测试改写期望。** 文件迁移或测试入口调整可以更新接入方式；在业务契约不变时，不应因变量名、组件层级或样式变化而改变 expected。测试失败先辨明业务回归、环境故障与过期断言，不自动迎合当前实现。

**H. 以最小充分证据为完成条件。** 类型检查通过不能证明数据流正确；用例数量、覆盖率或全绿不能替代上述证明。反过来，不为机械改动新增重复测试，不重测第三方已拥有且本项目未改变的内部行为，不为测试方便新增生产抽象。

### 3.4 UI/UE 验证的生命周期

- UI/UE 验证仍是开发责任，频繁变化意味着不固化，不意味着不检查。
- 按当前改动及直接影响范围选择浏览器、手工或临时自动化验证；不强制每次完整扫描所有页面与交互状态。
- 临时脚本、截图、录屏和夹具不进入正式测试目录或功能提交；使用临时目录，并在验证完成后清理。交付说明可记录验证范围与结论。
- 已有 UI 测试不能因新规则被无差别删除。对当前任务涉及的用例区分可保留的业务断言和应退出的 UI 断言；批量清理是单独维护任务。
- 如果环境缺失，明确未验证的 UI/UE 范围；不能用源码正则替代浏览器验证后声称交互已经通过。

## 4. 与测试配套的实现规则

测试能够发现错误，但不能代替实现边界。通用 Web 规则需要同步明确以下约束。

### 4.1 状态与异步提交

- 一份业务事实有明确的权威所有者；共享消费者通过订阅、输入或既有数据层读取。派生值不另建人工同步的可写镜像。
- 状态的代码位置、逻辑复用和运行时共享是三个不同问题；必须明确实例创建与销毁范围。
- 允许有业务语义的独立状态，如编辑草稿、历史快照与离线工作副本，但必须定义初始化、刷新、提交、取消及冲突边界。禁止把所有副本都视为错误。
- 查询身份覆盖实际影响结果的上下文；与身份匹配的结果才可提交。数据、错误与 loading 使用一致的有效性判断。
- 变更操作只写入自己拥有的字段与状态；更新或失效直接相关的权威来源。需要重新获取服务端结果时允许重取，不把“禁止强制刷新 UI”误解成禁止合理的数据失效。
- 错误状态不得无条件转换成正常业务空值；可选分区允许部分成功，但应保留失败信息。

### 4.2 复用与组件库

- 新增前检查同职责的现有组件、模块与库能力；稳定责任已有所有者时优先扩展现有契约，避免平行实现。
- 展示和交互复用归 Component，业务状态、查询、修改与流程复用归 Module。模块可以包含 UI；目录不强制每个功能建立完整分层。
- 多个页面共享业务能力时，其数据与生命周期约束应一起复用，而不是只抽出表格 DOM。页面自己的筛选、布局和编辑意图仍留在页面。
- 共享抽取以真实消费者、稳定契约和维护责任为依据，不按相似行数机械合并。只因看起来相似但语义不同的组件不强行统一。
- 采用项目既有 UI 库的公开组件和扩展接口；定制理由必须对应实际能力缺口，不能只是“手写更快”。复用项目封装时也要确认其实际语义，而非只看名称。

### 4.3 样式归属与旧实现退出

- 私有 DOM 与私有样式由同一个组件边界拥有；具体共置方式由框架 skill 定义。
- 不为缩短文件、绕过库样式或让某次效果生效，把私有规则提升为全局规则。
- 修改当前有效声明，合并被替代的同条件声明；主题、断点和状态变体可以有明确的覆盖关系，不能一律禁止 CSS 层叠。
- 功能移除或替换应同步退出不再需要的 DOM、样式、状态、监听和引用；不能以永久隐藏代替移除。
- 临时隐藏、延迟挂载、状态保留和真正删除应按生命周期选择。隐藏不自动意味着任务应继续运行，卸载也不自动代表已发请求失效。

## 5. 框架与组件库层的具体落实方向

本节属于 skills 的责任映射，不写入通用规范正文；以下 API 用于说明差异，不规定项目必须采用新的依赖。

### Vue 与相关状态/路由 skill

- 派生值使用 `computed`；不能用额外 `ref` 加双向 watcher 维护本可直接派生的镜像。把 prop 当前值传入 `ref` 只能得到初始化值，是否为独立草稿必须明确。
- 调用同一个 composable 不自动共享内部创建的 refs；共享状态须由共同所有者、注入或既有 store/query 机制提供。返回和消费响应式值时保留响应式连接。
- Pinia 的 state/getter 解构与 action 解构区别处理；不能为共享方便把页面临时草稿全部变成全局 store。目录内 store 的生命周期不由目录名决定。
- reactive 输入变化、同路由参数变化和销毁要进入实际 watcher/生命周期验证。状态复用和重置须覆盖真实框架运行，不能仅抽取回调验证后宣称生命周期正确。
- 私有模板与样式保留在 SFC；共享视觉能力先考虑共享组件，避免把局部 scoped 样式搬到全局文件。
- 测试数据行为时执行真实 store actions。使用 `createTestingPinia` 等辅助工具时注意默认 stub 行为，不能让被测 action 不执行。生命周期相关 composable 使用最小真实运行宿主，断言数据契约，不保留宿主 DOM 快照。

Vue 官方说明每次调用创建局部状态的 composable 会获得自己的状态实例，见 [Composables](https://vuejs.org/guide/reusability/composables)。Pinia 测试工具默认 stub actions 的边界见 [Testing stores](https://pinia.vuejs.org/cookbook/testing.html)。

### React

- 自定义 Hook 复用逻辑，不自动共享内部 state；需要共同状态时使用最近共同所有者或项目已有的 context/store/query 机制。
- 派生值在渲染中计算，只有实际需要时才缓存；不以 Effect 将 props 或查询结果复制成同步镜像。独立编辑草稿是有边界的例外。
- Effect 依赖反映真实数据上下文；不得通过省略依赖、任意 ref 或 memo 来掩盖重新同步的必要性。异步提交需判断有效期，不能只清理定时器。
- 用真实 Hook/组件运行环境验证订阅、重新渲染和清理行为；不能 mock React state/Effect 后宣称这些行为已验证。合适的最小宿主只是执行环境，不因此增加永久 UI 断言。
- 修改需遵守 React 的状态更新语义；测试不应把内部渲染次数或 Effect 次数当成业务契约。关键副作用按业务要求去重或幂等。
- 项目采用 CSS Modules 时，私有样式与所属组件同目录；不强制合并成 Vue 式单文件，也不把私有 CSS 移入页面巨型样式表。
- React 性能指导适用于正确性约束成立之后。减少依赖、缓存、并行请求和保留隐藏组件均需服从数据身份、生命周期及工作量边界。

依据：[Reusing Logic with Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks) 区分逻辑复用和状态共享；[Choosing the State Structure](https://react.dev/learn/choosing-the-state-structure) 说明冗余状态与镜像 props 的问题。

### Vuetify / Ant Design

- 两者都落实“先项目封装与库能力，后定制”，但组件映射、版本 API 与样式入口分别维护。
- Vuetify 的 model、表单、服务端表格和 activator slot 与 Vue 所有者连接；保留 slot 传入的事件及可访问性属性。具体语法以已安装主版本为准。
- Ant Design 的 Form、受控 value、Upload 文件列表、Table 分页/筛选/排序与 React 所有者连接；明确初始化值与后续更新的差异，避免控件内部状态与业务 state 双向复制。
- 服务端筛选、排序和分页使用服务端结果契约；控件不能再把分页子集当成完整集合重复执行业务筛选。控件事件到业务查询/命令的适配应有必要的数据行为测试。
- 样式优先使用各自的 theme/token/defaults、公开 prop/slot 或语义化样式接口；不依赖内部 DOM 和不断提高选择器优先级。
- 只验证本项目的接入与定制责任，不重测组件库内部实现。键盘、焦点、RTL、弹层与视觉呈现属于当次 UI/UE 验收，不因是第三方控件就免检，也不因此固化。

## 6. 与现有规范的协调

- 现行 `[web-persistent-test-scope]` 和 `[web-temporary-ui-tests]` 已确认长期测试范围与临时 UI 验证政策。本设计补足分类边界、数据流覆盖和质量门槛，不另建相反政策。
- 通用 `[test-addition]` 中提到 routes、forms、permissions，应解释为相关业务和数据行为变化值得验证，不能据此在 Web 项目新增永久 DOM/样式/交互呈现测试。
- 通用 E2E、snapshot 条款在 Web 场景仍受更具体的永久测试范围限制。业务数据快照是否有价值由数据契约决定；UI 源码和截图快照不固化。
- `[web-state-source]`、`[web-state-minimal]` 与编辑缓冲条款应补充运行时实例、数据身份和写入有效期，避免“同一个 store 名称就是同源”“所有复制都禁止”等误解。
- `[web-shared-component]` 与 `[abstraction-exception]` 的行数门槛需要协调。建议取消“显著减少总行数”作为正确复用的必要条件，以稳定责任、真实消费者、行为一致性和总体复杂度判断；此项是拟议规则调整，不在设计阶段视为已生效的例外。
- 不将本次范式逐一复制成跨层重复禁令。适合静态检查的内容由现有工具负责；时序与数据契约由行为测试负责；UI/UE 呈现由临时验收负责。

## 7. 设计验收标准

- 同一条通用政策只有一个权威定义，框架和组件库层能找到相应落实方向，且不反向削弱通用约束。
- 对任意新增前端测试，可以明确说出它保护的数据/业务契约、错误实现如何被识别、哪些依赖被替换以及尚未覆盖的运行边界。
- UI/UE 小调整不会要求批量更新长期断言；数据身份、提交参数或状态转换错误仍会让对应测试失败。
- 测试重点覆盖实际数据来源、传递、写入和消费者，不停留于格式化函数测试、源码匹配或 stub 调用次数。
- 规则保留合法编辑草稿、独立状态实例、CSS 状态变体和临时隐藏等必要边界，不为禁止一种错误制造另一种错误。
- 不以测试数量、覆盖率目标、引入工具或扩大抽象层次作为规则完成标准。
